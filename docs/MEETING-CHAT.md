# Meeting chat

During any group call or recurring meeting, choose **Chat**. Send text to participants currently connected with chat support. Use **Attach image or file** to offer an attachment to those participants. Each recipient chooses **Accept file** before transfer, then **Save file**. Received raster images up to 10 MiB can show a preview; other file types are downloadable without opening or executing them. Any file type is supported, with a 100 MiB attachment limit.

Chat is live and held in memory for the current call. Leaving, being kicked, signing out or closing the app clears it; joining later does not replay earlier messages. Files explicitly saved to disk remain. Existing clients retain their call functionality and require a new app/browser release to use chat. The ready-participant count indicates how many current participants support chat.

Messages and files travel on a separate reliable, ordered `pvp-group-chat` SCTP data channel in each existing DTLS-encrypted peer connection. They are sent directly to recipients, not through signaling or the video forwarding tree. No message or file payload is uploaded to DigitalOcean. The connection inspector still reports the peer connection's actual endpoints. Text and file content are separate from server moderation messages; peers cannot alter owner/admin privileges using chat.

The protocol (`v:1`) uses `hello`, `text`, `offer`, `accept`, `chunk`, `ack` and `cancel`. IDs are random 128-bit values. Sender identity is taken from the authenticated peer link and roster, never a sender field in a message. Text is rendered as literal text with a 4,000-character limit. Attachment metadata contains a sanitized basename, byte size and SHA-256 hash. Only accepted offers allocate receive state. Chunks contain up to 16 KiB of bytes encoded as base64, with contiguous offsets checked independently on each platform. Download/save becomes available only after all bytes arrive and the hash matches.

Transfers use backpressure, an approximately 256 KiB/s aggregate payload pacing budget per sender, one transfer at a time to each recipient, and 30-second stall timeouts. Incoming file payloads and retained received files share a 100 MiB memory budget; retained outgoing files have a separate 100 MiB budget. Clear an attachment to free its budget. Chat retains at most 200 entries, and channels rate-limit metadata and chunks. Cancelling or removing a peer stops incomplete transfers; leaving releases buffers and browser Blob URLs. Declined, expired or cancelled offers can be shared again as new offers.

Mac file selection and saving use sandboxed native Open/Save panels, with file size and regular-file checks and bounded reads. Filenames from a peer cannot choose a filesystem destination. Arbitrary file types are never automatically opened. These controls do not make saved files intrinsically safe; file interpretation remains with whatever application a user chooses afterward.

Verification covers live browser/browser and Mac/browser Unicode text, real chunked binary delivery and byte comparison, acceptance before transfer, image preview, literal HTML text, malformed metadata, unexpected offsets, corrupted hashes, memory limits, cancellation, departure, and session cleanup. Call, screen-share, persistent login, open-link and admin moderation regressions also pass. See the [release manifest](meeting-chat-release.json) for deployment details. Native file panels are compiled and code-reviewed; automated media tests use synthetic streams and do not validate physical microphones or WAN performance.
