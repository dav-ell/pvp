# Local red-team review — October 11, 2026

This review covers the repository's Rust signaling service, browser and Flutter client trust boundaries, optional legacy UDP media transport, and UDP relay. Adversarial tests use isolated local accounts and databases. No production service was attacked, deployed, or changed. Existing workspace changes were preserved.

## Findings and fixes

No critical finding was confirmed. The following high-severity findings were addressed in source:

| ID | Finding and attack prerequisite | Fix |
| --- | --- | --- |
| H1 | A signed-in account could reserve the shared 256 WebSocket slots with repeated upgrades/replacements. Reservations outlive the active peer-map entry, especially with slow writes and pending upgrades. Other accounts then receive 503. | Two lifetime connection permits per account, covering pending upgrades, active connections, replacement draining and close. Weak references prevent the account limiter map growing with historical accounts. |
| H2 | Signaling queues were capped by message count, not bytes. Up to 256 queues of 256 messages could retain gigabytes; even ICE payloads permit hundreds of MiB. Slow recipients and authorized group negotiation amplify this beyond the documented 150 MiB deployment limit. | Serialize messages before enqueueing and impose a shared 8 MiB byte budget. RAII permits stay reserved through the socket write and release on queue failure, teardown or consumption. A recipient whose signaling cannot be queued is disconnected. |
| H3 | WebSocket authentication occurred before upgrade, and replacement/teardown were outside the operation lock. A revoked pending upgrade could insert a peer and terminate a newer session's call. Checking the current connection before acquiring the operation lock also allowed a stale connection to pass its check before replacement. | Reauthenticate during installation under the operation lock; serialize installation, call/room cleanup and disconnect teardown; check connection identity after acquiring the same lock used for mutations and revocation. Preserve the terminal `replaced` message so older clients stop reconnecting. |
| H4 | Legacy UDP media used unauthenticated AES-CBC. An on-path attacker could modify ciphertext, IVs and fragment headers before native decoding. Arbitrary fragment counts and many partial sequences could amplify reassembly memory. | Versioned `PVP2` encrypt-then-MAC envelope with a domain-separated HMAC-SHA-256 key and constant-time tag verification over version, header, IV and ciphertext before parsing or decrypting. Completed-frame replay windows, 32 partial frames per media type, and fragment limits of 1,024 video / 16 audio; sender uses the same limits. |
| H5 | The UDP relay front allocated a socket and reader task for every distinct source address before authentication. Cleanup removed map entries but readers waited forever, keeping sockets alive. Spoofed or rotating source addresses could exhaust file descriptors and memory. | Cap live reader/socket lifetimes at 256 with owned permits; readers check idle expiry and exit, closing sockets and releasing capacity. Bound durable relay rooms to 256. Backend responses must originate from one of the configured backend endpoints. |

Dependency hardening: upgraded the optional legacy `ringbuf` lock from 0.4.8 to 0.5.3, above the 0.5.2 security fix in [RUSTSEC-2026-0293](https://rustsec.org/advisories/RUSTSEC-2026-0293.html). The documented panic-in-destructor trigger does not apply to the app's `f32` elements, but keeping an affected dependency was unnecessary.

## Compatibility and limits

Browser/native signaling fields, HTTP routes and the database schema remain compatible. One active device remains the policy; two reservations allow the previous device to drain during takeover. Slow peers or excess reservations can be rejected deliberately rather than exhausting the service.

Legacy UDP peers must both be rebuilt: authenticated packets are intentionally incompatible with old unauthenticated media. There is no downgrade fallback. The relay forwards the envelope unchanged. Rotate the legacy shared media key between calls; the replay window protects a receiver lifetime, not freshness across process restarts with a reused static key. The optional relay's control protocol still uses a shared bearer token over UDP; this change does not redesign its authentication or provide forward secrecy.

Source fixes do not update existing `dist/` binaries, installed apps, or production deployments. Review findings are evidence for the paths examined, not a guarantee that no other vulnerability exists. Physical capture, native codec fuzzing, OS configuration, deployed proxy configuration and bundled WebRTC binaries were not independently audited.

## Validation

- Root Rust: packet-envelope regressions reject every mutated byte, all truncated envelopes, incorrect keys and old unversioned packets; replay tests cover reordering, bounds and sequence wrap.
- Signaling Rust: per-account reservations cannot consume another account's quota; shared queued-byte reservations release on dropped queues and failed sends; existing admission, moderation, session, authorization and encryption tests pass.
- Relay Rust: real UDP sockets prove capacity rejection, idle-reader termination, ability to rebind expired backend ports and capacity reuse.
- Browser: full existing 31-test suite passed; additional socket-replacement regression verifies the old peer receives `replaced` and closes while the new peer remains usable.
- Root/signaling/relay strict Clippy checks pass.
- `npm audit`: zero advisories. OSV scanned 393 pinned versions: no modern-client advisories, and only legacy maintenance notices for `audiopus_sys` and `paste` remain.
- The patched ring-buffer API was independently compiled and exercised with the app's `HeapProd<f32>` / `HeapCons<f32>` aliases and audio push/pop calls.
- Full legacy build initially could not find OpenCV development libraries. The envelope/replay library is tested independently of OpenCV; this limitation prevents claiming a verified legacy media build.

- Native integration built and launched the Mac test app, established the first call and saved its live inspector screenshot, but did not complete after several minutes. The launched test app was stopped; the suite is unverified, not reported as passing. No Flutter client source was changed.

Final local results: 26 Rust tests passed (2 root, 20 signaling, 4 relay); all 31 pre-existing browser tests passed, plus the new replacement regression in a 10-test security rerun. Strict Clippy passed for the root, signaling and relay crates. The full legacy native-codec build and the complete native UI integration remain unverified.

## Authentication, credentials and SQLite follow-up

A closer review found that database confidentiality depended on the launcher: systemd has `UMask=0077`, but direct and Docker starts could create a 0644 database under a normal umask. The service now creates and repairs its SQLite database, WAL, SHM and rollback journal to 0600 on Unix. It rejects symlinks, hardlinks, special files, files owned by another user and directory ancestry that permits another user to replace the files. Canonical directory paths preserve macOS system aliases without allowing SQLite to follow a final database symlink. Docker's new `/data` directory is 0700. Existing mounted volumes must also have safe directory ownership and modes; unsafe paths fail startup rather than silently bypassing the checks.

Login now has a normalized per-username limit of 30 verification attempts per 15 minutes, in addition to the existing per-IP budget and two password-hashing worker slots. Both existing and unknown usernames use the gate, and case/whitespace variations do not evade it. This is a temporary throttle; a targeted flood can deny sign-in for its duration. In-memory rate limits reset on restart and are not shared across server instances.

Passwords use per-user random salts and Argon2id v19 with 19 MiB memory, two iterations and one lane, matching the [OWASP minimum](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Passwords are not stored in plaintext or saved in browser localStorage or native preferences. Native sign-in tokens use device-only Keychain storage. Production HTTPS cookies are HttpOnly, Secure and SameSite=Strict; loopback development cookies omit Secure. Tokens are random, and SQLite stores only SHA-256 hashes. A copied hash cannot be sent as a cookie to authenticate. Idle sessions expire after 30 days, sliding with activity; there is no absolute maximum lifetime for an active session.

SQL uses bound parameters for account and application input, and the HTTP router does not serve arbitrary filesystem files or the database. The systemd service uses an unprivileged account, a private state directory and filesystem restrictions. These are configuration/source observations, not a fresh inspection of the production VM.

Portable backups now remove all session rows after the online snapshot while retaining users, password hashes, friends, meetings and history. Restoring a new backup therefore requires users to sign in again instead of reviving a session revoked after the snapshot. The live database is unchanged. Older backups are not retroactively sanitized.

**SQLite and these backups remain unencrypted.** Someone who can copy them can read usernames, display names, friendship relationships, meetings and call history, and can try to crack password hashes offline. Strong hashing increases the cost but does not protect weak/reused passwords completely. File permissions do not protect against root, a compromised service account, stolen readable backups or an unencrypted disk image. Encrypt the production volume and backup storage if protection against stolen snapshots/disks is required; application database encryption would require separately managed keys. Media and plaintext passwords are not in the database.

Product gaps remain: no MFA/passkeys, user-facing password change/reset or sign-out-all-devices control. This review does not claim protection against compromised endpoints or a writable/tampered database. Replacing a writable account database can replace password hashes and authorization data; preventing that relies on the host security boundary.

Validation: two real-file Rust regressions cover main/WAL/SHM modes, permissive-file repair, symlink/hardlink rejection and unsafe directory ancestry. Browser regressions verify distinct salted Argon2id hashes, absence of raw session tokens in SQLite, rejection of a stolen session hash as a cookie, SQL-injection login failure, private live files, session-free backups with unchanged live accounts/sessions, and an account throttle across 31 distinct forwarded source addresses. The targeted security/session/meeting run passed all 16 tests; 22 signaling Rust tests and strict signaling Clippy passed. No production files, backups or deployments were changed.
